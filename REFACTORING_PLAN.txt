Fly-in refactoring plan for current code
=======================================

This plan is based on the current files:
- pygame_common.py is empty.
- pygame_standard.py and pygame_airlines.py both define their own pygame rules.
- Both pygame files currently import/use AgentRefueling, but events.py defines
  AgentInTransit and simulation.py emits AgentInTransit.

Important: fix the event mismatch before doing DRY refactoring. Otherwise you
will move broken logic into common files and make the bug harder to see.


1. Fix before refactoring
-------------------------

Problem:
- pygame_standard.py imports AgentRefueling.
- pygame_airlines.py imports AgentRefueling.
- events.py does not define AgentRefueling.
- simulation.py emits AgentInTransit.
- visualizers.py already uses AgentInTransit.

Recommended fix:
- Replace AgentRefueling with AgentInTransit in both pygame files.
- Keep one event name across the project unless you intentionally rename it
  everywhere.

Good comment near the pygame event handling:
    "Long-distance movement is represented by AgentInTransit events. The
    visualizer only decides how to draw that transit state."

Why first:
The pygame visualizers may fail at import time before any refactor can be
tested.


2. Rebuild pygame_common.py slowly
----------------------------------

pygame_common.py is currently empty, so use it only for shared code that is
already duplicated in both pygame visualizers. Do not make it a dumping ground.

Start with these shared definitions:

    PositionKind = Literal["zone", "connection"]

    @dataclass(frozen=True)
    class DroneDisplayPosition:
        kind: PositionKind
        first_zone: str
        second_zone: str | None = None

    Point = tuple[int, int]
    IMG_DIR = Path(__file__).resolve().parent / "img"

Good top-of-file comment:
    "Shared pygame helpers live here only when at least two pygame visualizers
    use the same concept. View-specific layout stays in the window class."

Why:
PositionKind, DroneDisplayPosition, Point, and IMG_DIR are repeated now and are
safe to centralize.


3. Centralize colors and constants, but keep it small
----------------------------------------------------

Current duplication:
- Many RGB tuples are repeated in pygame_standard.py and pygame_airlines.py.
- Standard mode has MAP_ZONE_COLORS.
- Airlines mode has hard-coded colors for weather, controls, sidebar, badges.
- width/height/FPS/turn delay are also repeated.

Add to pygame_common.py:

    class UIColors:
        WHITE = (255, 255, 255)
        BLACK = (0, 0, 0)
        GREEN = (46, 204, 113)
        BLUE = (52, 152, 219)
        RED = (231, 76, 60)
        YELLOW = (241, 196, 15)
        CYAN = (0, 188, 212)
        DARK_PANEL = (31, 38, 46)
        TEXT_LIGHT = (230, 237, 245)
        TEXT_MUTED = (140, 152, 168)
        ZONE_BORDER = (45, 55, 72)

    class UIConstants:
        FPS = 60
        STANDARD_WIDTH = 1200
        STANDARD_HEIGHT = 800
        TURN_DELAY_MS = 600
        AIRLINES_TURN_DELAY_MS = 1000
        BADGE_RADIUS_MIN = 8

    PYGAME_ZONE_COLORS = {...}

Avoid:
- Do not move SimulationConfig values here. SimulationConfig is for movement
  rules; UIConstants is for drawing and playback.
- Do not try to share ANSI terminal colors with pygame colors.


4. Extract image loading helpers
--------------------------------

Current duplication:
- pygame_standard.py loads, scales, and color-keys drone.png directly.
- pygame_airlines.py has two almost identical functions:
  _load_drone_sprite() and _load_car_sprite().

Add small helpers to pygame_common.py:

    load_sprite(filename, size, color_key=None) -> pygame.Surface | None
    load_outlined_sprite(filename, size, final_size=(32, 32)) -> pygame.Surface | None
    load_scaled_image(filename, size) -> pygame.Surface | None

Then:
- standard mode can use load_sprite("drone.png", (30, 30), UIColors.WHITE)
- airlines mode can use load_outlined_sprite("drone.png", (26, 26))
- airlines mode can use load_outlined_sprite("car.png", (25, 25))

Keep _load_background() inside AirlinesWindow for now because the germany/europa
choice depends on CLI/map behavior.

Good comment near load_outlined_sprite:
    "The outline is generated from the sprite alpha mask so map icons stay
    readable over busy backgrounds."


5. Extract one badge drawing helper
-----------------------------------

Current duplication:
- pygame_standard.py draws a red count badge when many drones share a point.
- pygame_airlines.py draws the same badge.

Add to pygame_common.py:

    def draw_count_badge(screen, font, point, count) -> None:
        if count <= 1:
            return
        ...

Use it from both visualizers.

Good comment:
    "Single vehicles do not need a badge; the badge only explains grouped
    drones at the same screen point."

Why this is a good first DRY step:
It is small, visual-only, and very unlikely to affect simulation behavior.


6. Split pygame_standard.py draw()
----------------------------------

Current problem:
DroneSimulationWindow.draw() does too much:
- clears the screen
- builds active connection state
- counts duplicate paths
- draws connections
- calculates label row offsets
- draws zones
- groups drones
- draws drone sprites and count badges
- draws challenger hint

Split into private methods:
- _active_connections(frame)
- _draw_connections(active_connections)
- _build_row_label_indices()
- _draw_zones(row_label_indices)
- _group_drones(frame)
- _draw_drone_groups(drone_groups)
- _draw_challenger_hint_if_needed()

Keep these methods inside DroneSimulationWindow. No new class needed.

Good comment above draw():
    "The draw step is intentionally ordered back-to-front: panel, connections,
    zones, vehicles, then optional hints."

Good comment near parallel connection offset:
    "Repeated edges are nudged sideways so parallel links do not hide each
    other."


7. Split pygame_airlines.py __init__()
--------------------------------------

Current problem:
AirlinesWindow.__init__ mixes:
- pygame window setup
- layout sizes
- font setup
- asset loading
- start hub lookup
- flight data initialization
- turn index building
- playback state
- first replay jump

Split into:
- _setup_layout()
- _setup_pygame()
- _load_assets()
- _find_start_hub_name()
- _initialize_flight_data()
- _build_turn_indices()
- _setup_playback_state()

Good comment near _build_turn_indices():
    "Turn indices let the UI seek by turn without replaying the simulator."


8. Split pygame_airlines.py _draw_map()
---------------------------------------

Current problem:
_draw_map() draws both connection/weather layers and city layers.

Split into:
- _draw_weather_connections()
- _draw_weather_icon(connection, condition)
- _draw_city(zone)
- _draw_city_name(zone)
- _draw_population_label(zone)

Good comment near city drawing:
    "Airlines mode uses the map coordinates directly; standard mode rescales
    coordinates into a viewport."


9. Split pygame_airlines.py _draw_drones()
------------------------------------------

Current problem:
_draw_drones() resolves positions, detects road-vs-air route, groups drones,
draws vehicles, and draws badges.

Split into:
- _zone_points()
- _resolve_drone_point(pos)
- _is_road_segment(first_zone, second_zone)
- _group_vehicles_by_point()
- _draw_vehicle_group(point, is_car, labels)

Use the shared draw_count_badge() after this split.

Good comment near _is_road_segment():
    "Transport type is presentation logic here; simulation still uses the same
    connection and movement events."


10. Split pygame_airlines.py _draw_sidebar()
--------------------------------------------

Current problem:
_draw_sidebar() handles header, weather alerts, departures, flight status, and
card drawing in one function.

Split into:
- _draw_sidebar_background()
- _draw_sidebar_header()
- _draw_weather_alerts(y)
- _draw_live_departures(y)
- _determine_flight_status(info)
- _draw_departure_card(y, drone_label, info, status)

Good comment near _determine_flight_status():
    "Status text is presentation-only. The real route state comes from replayed
    simulation events."


11. Keep event collection simple
--------------------------------

Current duplication:
- PygameStandardVisualizer and PygameAirlinesVisualizer both store graph and
  event_queue and append events.

Optional helper:

    class PygameEventCollector(EventListener):
        def __init__(self, graph: Graph) -> None:
            self.graph = graph
            self.event_queue: list[SimulationEvent] = []

        def handle(self, event: SimulationEvent) -> None:
            self.event_queue.append(event)

Use it only after the AgentInTransit/AgentRefueling mismatch is fixed.

Avoid:
Do not build a large visualizer base class. One tiny event collector is enough.


12. Simulation refactor comes after pygame import works
------------------------------------------------------

Simulator._execute_turn() is still the biggest domain function. It can be split
later, but pygame currently has a real event-name problem, so fix the UI imports
first.

Suggested split:
- _finish_in_transit_drones(turn, zone_occupancy, moved_drone_ids)
- _plan_departures(connection_usage, moved_drone_ids)
- _count_outgoing_by_zone(planned_moves)
- _apply_planned_moves(turn, planned_moves, zone_occupancy, outgoing_counts)

Good comment above _execute_turn() after splitting:
    "A turn is processed in phases: finish existing transit, plan departures
    from a stable snapshot, then apply moves that pass capacity checks."

Also replace this current comment:
    "Replaced the redundant _calculate_transit_time with our clean pathfinder
    method"

With:
    "Pathfinder owns travel-time rules, including distance and weather."

Why:
The current comment talks about an old refactor. Future readers need to know
the rule, not the history.


13. Parser cleanup is lower priority
------------------------------------

Parser.parse() repeats start_hub/end_hub/hub handling. It is not the biggest
problem and it is currently readable.

Later helper:
- _parse_and_add_zone(graph, line, line_num, is_start=False, is_end=False)

Good comment near metadata parsing:
    "Metadata is optional and is stripped before the base map line is parsed."


Recommended order
-----------------

1. Replace AgentRefueling with AgentInTransit in both pygame files.
2. Add minimal shared types/constants to pygame_common.py.
3. Add shared image loading helpers.
4. Add shared draw_count_badge().
5. Split pygame_standard.py draw().
6. Split pygame_airlines.py __init__(), _draw_map(), _draw_drones().
7. Split pygame_airlines.py _draw_sidebar().
8. Add PygameEventCollector only if the duplicated event_queue code still feels
   worth removing.
9. Split Simulator._execute_turn().
10. Clean Parser.parse() only after the visualizer refactor is stable.


Do not overengineer
-------------------

- Do not make a pygame component framework.
- Do not merge terminal visualizers with pygame visualizers.
- Do not make pygame_common.py own every color or magic number immediately.
- Do not create new classes when a private helper function makes the code clear.
- Do not refactor simulation behavior at the same time as pygame drawing logic.
